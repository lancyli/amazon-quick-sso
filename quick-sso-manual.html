3Keycloak 配置 SAML Attribute Mapping

路径：客户端 → urn:amazon:webservices → 客户端范围 → 映射 → 配置新映射

Mapper类型SAML Attribute Name用途
AWS RoleHardcoded Attribute.../SAML/Attributes/RoleRole ARN + Provider ARN（逗号分隔，无空格）
Session RoleUser Property (email).../SAML/Attributes/RoleSessionName会话标识，URL 必须填在 Attribute Name 字段
PrincipalTag EmailUser Property (email).../SAML/Attributes/PrincipalTag:EmailQuick 强制要求，缺失报 invalid principal tag
⚠️
逗号前后不可有空格；Role ARN 在前，Provider ARN 在后。URL 必须填在 SAML Attribute Name 字段，不是 Friendly Name。

5AWS IAM 创建 Federation Role

操作人：AWS 管理员耗时：约 10 分钟

5.1 创建角色

受信任实体类型SAML 2.0 联合身份验证
访问级别✅ 允许编程访问和 AWS 管理控制台访问
角色名称<ROLE_NAME>

5.2 编辑 Trust Policy（添加 sts:TagSession）

{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Principal": {
                "Federated": "arn:aws:iam::<AWS_ACCOUNT_ID>:saml-provider/<SAML_PROVIDER_NAME>"
            },
            "Action": [
                "sts:AssumeRoleWithSAML",
                "sts:TagSession"
            ],
            "Condition": {
                "StringEquals": {
                    "SAML:aud": "https://signin.aws.amazon.com/saml"
                }
            }
        }
    ]
}
⚠️
必须加 sts:TagSession！因为 SAML 断言中包含 PrincipalTag:Email，没有此权限会报 "Not authorized to perform sts:AssumeRoleWithSAML"。

5.3 添加权限策略（CloudShell CLI）

aws iam put-role-policy \
  --role-name <ROLE_NAME> \
  --policy-name QuickFederationPolicy \
  --policy-document '{
    "Version": "2012-10-17",
    "Statement": [
      {
        "Sid": "SamlAutoProvision",
        "Effect": "Allow",
        "Action": "quicksight:CreateUser",
        "Resource": "*"
      },
      {
        "Sid": "ManageUsersAndRoles",
        "Effect": "Allow",
        "Action": [
          "quicksight:RegisterUser",
          "quicksight:UpdateUser"
        ],
        "Resource": "arn:aws:quicksight:us-east-1:<AWS_ACCOUNT_ID>:user/default/*"
      }
    ]
  }'
💡
如需创建 Author Pro 用户，将 quicksight:CreateUser 替换为 quicksight:CreateAuthorPro（仅 CLI 支持）。不要在 IAM 控制台 UI 编辑此策略。

常见问题排查

"Client not found"
Keycloak SAML 客户端未配置 IDP 发起的 SSO URL 名称 → 填写 urn:amazon:webservices
"Your request included an invalid SAML response"
缺少 Mapper 或格式错误 → 检查 3 个 Mapper 是否齐全；Role ARN 逗号无空格；开启"签署断言"
"RoleSessionName is required"
URL 填到了 Friendly Name 里 → 必须填在 SAML Attribute Name 字段
"invalid principal tag"
缺少 PrincipalTag:Email Mapper → 添加第 3 个 Mapper
"Not authorized to perform sts:AssumeRoleWithSAML"
Trust Policy 缺少 sts:TagSession → 编辑信任策略添加
Desktop redirect_uri_mismatch
OIDC 客户端 Redirect URI 不匹配 → 精确设置为 http://localhost:18080，末尾不加 /
Desktop 频繁要求重新登录
未启用 Refresh Token 或 offline_access scope → Keycloak OIDC 客户端启用两者

安全注意事项

TLS 证书IdP 端点必须使用 CA 签发的 HTTPS 证书，自签名证书会导致 token exchange failed
用户 email 一致性Keycloak 用户 email = Quick Web NameID email = Desktop id_token email，三者须完全一致（大小写敏感）
Email VerifiedKeycloak 用户的 Email Verified 开关必须为 ON

Keycloak 集成企业 Active Directory 配置手册

Keycloak 作为 Amazon Quick 的 IdP，用户从企业 AD 自动同步 · v1.0

架构概述

┌──────────────────────────────────────────────────────────────┐
│               企业 Active Directory                            │
│    用户、组、密码、属性的唯一权威数据源                          │
│    （入职/离职/改密码/调部门 全部在 AD 操作）                    │
└──────────────────────┬───────────────────────────────────────┘
                       │ LDAP/LDAPS (389/636)
                       │ ① 定时同步用户/组
                       │ ② 实时验证密码（委托认证）
                       ▼
┌──────────────────────────────────────────────────────────────┐
│               Keycloak (协议转换层)                             │
│    角色：把 AD 身份翻译为 SAML/OIDC 协议                        │
│    不存储密码，密码验证委托给 AD                                 │
│                                                               │
│    ┌─────────────┐              ┌─────────────┐              │
│    │ SAML 客户端  │              │ OIDC 客户端  │              │
│    │ (Quick Web) │              │ (Desktop)   │              │
│    └──────┬──────┘              └──────┬──────┘              │
└───────────┼────────────────────────────┼─────────────────────┘
            │ SAML 断言                   │ OIDC Token
            ▼                            ▼
     Amazon Quick Web              Amazon Quick Desktop
💡
核心理念： AD 是"数据源"，Keycloak 是"翻译官"（用 LDAP 和 AD 对话，用 SAML/OIDC 和 AWS 对话），Quick 是"消费方"。

同步类型触发方式作用

7SPNEGO 免密单点登录（可选）

适用场景：域内 Windows 电脑访问 Keycloak 登录页时自动完成认证，无需输入用户名密码。

域内 Windows 电脑（已登录 AD 账号）
    → 浏览器访问 Keycloak 登录页
    → 浏览器自动发送 Kerberos Ticket（SPNEGO 协议）
    → Keycloak 验证 Ticket → 自动登录成功
    → 用户全程无感，不输密码
✅
非域设备（Mac/手机/非域 Windows）自动降级为密码登录，不影响正常使用。

关键配置点

SPN 注册setspn -S HTTP/<KEYCLOAK_DOMAIN> svc-keycloak-http
keytab 生成ktpass 命令生成 keytab（会重置服务账号密码）
Keycloak 配置LDAP Provider 中开启 Kerberos，指定 Realm / Server Principal / Key Tab
浏览器配置通过 GPO 将 Keycloak 域名加入 Intranet 信任区 / AuthServerAllowlist
⚠️
NTP 时钟同步：Keycloak 服务器与域控时钟偏差须 < 5 分钟（Kerberos 硬性要求）。SPN 中域名必须与实际访问域名完全一致。

常见问题排查

Test connection 失败
网络不通或端口被阻 → 确认 Keycloak 能连通 AD:389/636
Test authentication 失败
Bind DN 或密码错误 → 检查 DN 格式（须完整 CN=xxx,OU=xxx,DC=xxx）
同步 0 个用户
Users DN 配置错误 → 确认 DN 路径正确，Search scope 为 Subtree
用户同步了但 email 为空
AD 中 mail 属性未填写 → 需 AD 管理员补充
Email verified = OFF 导致 Quick 登录失败
添加 hardcoded-attribute-mapper 设置 emailVerified=true
LDAPS 连接失败
证书不受信任 → 导入 AD CA 证书到 Keycloak TrustStore
