5AWS IAM 创建 Federation Role

操作人：AWS 管理员耗时：约 10 分钟

5.1 创建角色

IAM → 角色 → 创建角色

受信任实体类型SAML 2.0 联合身份验证
SAML 2.0 提供商选择 <SAML_PROVIDER_NAME>
访问级别勾选 ✅ 允许编程访问和 AWS 管理控制台访问
权限策略跳过（下一步用 CLI 添加）
角色名称<ROLE_NAME>

5.2 编辑 Trust Policy（添加 sts:TagSession）

IAM → 角色 → <ROLE_NAME> → 信任关系 → 编辑信任策略：

{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Principal": {
                "Federated": "arn:aws:iam::<AWS_ACCOUNT_ID>:saml-provider/<SAML_PROVIDER_NAME>"
            },
            "Action": [
                "sts:AssumeRoleWithSAML",
                "sts:TagSession"
            ],
            "Condition": {
                "StringEquals": {
                    "SAML:aud": "https://signin.aws.amazon.com/saml"
                }
            }
        }
    ]
}
⚠️
必须加 sts:TagSession！因为 SAML 断言中包含 PrincipalTag:Email，没有此权限会报 "Not authorized to perform sts:AssumeRoleWithSAML"。

5.3 添加权限策略（CloudShell CLI）

打开 AWS CloudShell 执行：

aws iam put-role-policy \
  --role-name <ROLE_NAME> \
  --policy-name QuickFederationPolicy \
  --policy-document '{
    "Version": "2012-10-17",
    "Statement": [
      {
        "Sid": "SamlAutoProvision",
        "Effect": "Allow",
        "Action": "quicksight:CreateUser",
        "Resource": "*"
      },
      {
        "Sid": "ManageUsersAndRoles",
        "Effect": "Allow",
        "Action": [
          "quicksight:RegisterUser",
          "quicksight:UpdateUser"
        ],
        "Resource": "arn:aws:quicksight:us-east-1:<AWS_ACCOUNT_ID>:user/default/*"
      }
    ]
  }'
⚠️
注意事项：
· SamlAutoProvision 使用 Resource: "*" 确保 SAML 首次登录自动创建不受 ARN 格式限制
· ManageUsersAndRoles 使用 user/default/* 限定范围到 default 命名空间
· 如需创建 Author Pro 用户，将 quicksight:CreateUser 替换为 quicksight:CreateAuthorPro（仅 CLI 支持，控制台不识别此 Action）
· 不要在 IAM 控制台 UI 编辑此策略（编辑器不识别部分 Action 名称和 Resource 变量）

常见问题排查

"Client not found"
原因：Keycloak SAML 客户端未配置 IDP 发起的 SSO URL 名称。解决：填写 urn:amazon:webservices
"Your request included an invalid SAML response"
原因：缺少 Mapper 或格式错误。解决：检查 3 个 Mapper 是否齐全；检查 Role ARN 逗号无空格；开启"签署断言"
"RoleSessionName is required"
原因：RoleSessionName Mapper 的 URL 填到了 Friendly Name 里。解决：URL 必须在 SAML Attribute Name 字段
"invalid principal tag"
原因：缺少 PrincipalTag:Email Mapper。解决：添加第 3 个 Mapper
"Not authorized to perform sts:AssumeRoleWithSAML"
原因：Trust Policy 缺少 sts:TagSession。解决：编辑信任策略添加 sts:TagSession
"必须拥有 quicksight:CreateUser 权限"
原因：IAM Policy 中 Resource ARN 格式错误。解决：CreateUser 使用 Resource: "*"；或确认 ARN 格式正确
Desktop redirect_uri_mismatch
原因：OIDC 客户端 Redirect URI 不匹配。解决：精确设置为 http://localhost:18080，末尾不加 /
Desktop 频繁要求重新登录
原因：未启用 Refresh Token 或 offline_access scope。解决：Keycloak OIDC 客户端启用 Refresh Token + offline_access
Desktop Token validation failure
原因：Issuer URL 配置错误。解决：确认 Extension Access 中 Issuer URL 与 Keycloak .well-known 返回的 issuer 完全一致

安全注意事项

TLS 证书IdP 端点必须使用 CA 签发的 HTTPS 证书，自签名证书会导致 token exchange failed
安全组/防火墙如 Keycloak 部署在私有网络，需放行 /realms/{realm}/protocol/openid-connect/certs 公开访问（us-east-1）；如通过 CloudFront 公网暴露则无需额外配置
用户 email 一致性Keycloak 用户 email = Quick Web NameID email = Desktop id_token email，三者必须完全一致（大小写敏感）
Email VerifiedKeycloak 用户的 Email Verified 开关必须为 ON

Keycloak 集成企业 Active Directory 配置手册

Keycloak 作为 Amazon Quick 的 IdP，用户从企业 AD 自动同步，无需手动创建 · v1.0

架构概述

┌──────────────────────────────────────────────────────────────┐
│               企业 Active Directory                            │
│    用户、组、密码、属性的唯一权威数据源                          │
│    （入职/离职/改密码/调部门 全部在 AD 操作）                    │
└──────────────────────┬───────────────────────────────────────┘
                       │ LDAP/LDAPS (389/636)
                       │ ① 定时同步用户/组
                       │ ② 实时验证密码（委托认证）
                       ▼
┌──────────────────────────────────────────────────────────────┐
│               Keycloak (协议转换层)                             │
│    角色：把 AD 身份翻译为 SAML/OIDC 协议                        │
│    不存储密码，密码验证委托给 AD                                 │
│                                                               │
│    ┌─────────────┐              ┌─────────────┐              │
│    │ SAML 客户端  │              │ OIDC 客户端  │              │
│    │ (Quick Web) │              │ (Desktop)   │              │
│    └──────┬──────┘              └──────┬──────┘              │
└───────────┼────────────────────────────┼─────────────────────┘
            │ SAML 断言                   │ OIDC Token
            ▼                            ▼
     Amazon Quick Web              Amazon Quick Desktop
💡
核心理念：
· AD 是"数据源"（用户在哪里）
· Keycloak 是"翻译官"（用 LDAP 和 AD 对话，用 SAML/OIDC 和 AWS 对话）
· Quick 是"消费方"（接收翻译后的身份信息）

2.4 用户过滤（控制谁能访问 Quick）

通过 AD 用户组过滤，只同步特定组的成员到 Keycloak，不在组里的 AD 用户无法登录 Quick。

Infra 团队操作： 在 AD 中创建用户组（如 <QUICK_USERS_GROUP>），将允许使用 Quick 的人加入该组。

应用层团队操作： 在 Keycloak LDAP 配置中添加用户过滤条件：

User LDAP Filter(memberOf=CN=<QUICK_USERS_GROUP>,OU=Groups,DC=<domain>,DC=<tld>)
⚠️
DC=<domain>,DC=<tld> 需替换为实际的域名后缀。组名 <QUICK_USERS_GROUP> 和 OU 路径按实际 AD 结构调整。

效果：

  • Keycloak 只同步 <QUICK_USERS_GROUP> 组的成员，其他 AD 用户完全不出现在 Keycloak 中
  • 不在组里的人无法通过 SSO 登录 Quick
  • 后续增减人员由 Infra 团队在 AD 侧操作即可，应用层无需变更

高可用与安全建议

多域控支持

如果企业有多台域控制器，可配置 Failover：

Connection URLldaps://<DC1_FQDN>:636 ldaps://<DC2_FQDN>:636
💡
用空格分隔多个 URL，Keycloak 会依次尝试（Failover 模式）。

LDAPS 证书信任

如果 AD 使用自签名证书的 LDAPS (636)：

  1. 导出 AD 的 CA 证书
  2. 导入到 Keycloak 的 Java TrustStore： 
    keytool -importcert \
  -alias ad-ca \
  -file ad-ca-cert.pem \
  -keystore /opt/keycloak/conf/truststore.jks \
  -storepass changeit \
  -noprompt
  3. 在 Keycloak 启动参数中指定 TrustStore（或在 EKS 中通过环境变量配置）

网络安全

项目建议
端口优先使用 LDAPS (636)，避免明文传输密码
网络隔离Keycloak 所在子网需与 AD 域控在同一 VPC 或通过 VPN/VPC Peering 连通
服务账号权限最小权限原则，只赋予读取 Users/Groups 的权限

同步机制详解

同步类型触发方式作用
Full Sync每 24 小时自动 / 手动触发全量比对 AD 与 Keycloak 用户，添加新用户、更新变更、标记删除
Changed Users Sync每 5 分钟自动仅同步 AD 中 whenChanged 时间戳晚于上次同步的用户
登录时同步用户每次登录Keycloak 实时从 AD 获取最新属性（如 email、组变更）

用户离职处理

AD 操作Keycloak 反应Quick 影响
禁用账号下次同步时用户被标记为 disabled无法登录 Quick
删除账号下次 Full Sync 时用户从 Keycloak 中移除无法登录 Quick
修改密码实时生效（Keycloak 委托 AD 验证密码）下次登录使用新密码
移出 Quick 组下次同步后失去 Quick 角色无权限访问 Quick

常见问题排查

Test connection 失败
原因：网络不通或端口被阻。解决：确认 Keycloak 能 telnet 到 AD:389/636
Test authentication 失败
原因：Bind DN 或密码错误。解决：检查 DN 格式（必须完整 CN=xxx,OU=xxx,DC=xxx）和密码
同步 0 个用户
原因：Users DN 配置错误。解决：确认 DN 路径正确，Search scope 为 Subtree
用户同步了但 email 为空
原因：AD 中 mail 属性未填写。解决：让 AD 管理员补充用户的 mail 字段
登录报"Invalid credentials"
原因：账号被锁定 / 密码过期 / 账号禁用。解决：在 AD 中检查账号状态
Email verified = OFF 导致 Quick 登录失败
原因：AD 同步用户默认未验证 email。解决：添加 hardcoded-attribute-mapper 设 emailVerified=true
组同步不完整
原因：Groups DN 不包含所需组。解决：确认 Groups DN 覆盖目标 OU
LDAPS 连接失败
原因：证书不受信任。解决：导入 AD CA 证书到 Keycloak TrustStore

与 Quick SSO 的完整链路

配置完成后，完整的认证流程为：

1. 用户访问 Quick Web / Desktop
2. 跳转到 Keycloak 登录页
3. 用户输入 AD 用户名 + AD 密码
4. Keycloak 通过 LDAP Bind 向 AD 验证密码
5. AD 返回验证结果 + 用户属性（email、姓名、组）
6. Keycloak 生成 SAML 断言（Web）或 OIDC Token（Desktop）
7. Quick 接收 Token，通过 email 识别用户身份
8. 用户成功进入 Quick
✅
用户感知： 和直接在企业门户登录一样的体验——输入 AD 账号密码即可，无需额外注册或记忆新密码。

7SPNEGO 免密单点登录（可选，域内电脑自动登录）

适用场景：域内 Windows 电脑用户访问 Keycloak 登录页时自动完成认证，无需输入用户名密码。前提：用户电脑已加入域，使用域账号登录 Windows。

7.1 原理

域内 Windows 电脑（已登录 AD 账号）
    → 浏览器访问 Keycloak 登录页
    → 浏览器自动发送 Kerberos Ticket（SPNEGO 协议）
    → Keycloak 验证 Ticket → 自动登录成功
    → 用户全程无感，不输密码
✅
非域设备（Mac/手机/非域 Windows）：自动降级为密码登录（步骤 1-6 的 LDAP 方式），不影响正常使用。

7.2 AD 侧配置（Infra 团队操作）

7.2.1 创建 SPNEGO 专用服务账号

在 AD 中新建一个独立的服务账号（建议与 LDAP 账号分开）：

账号名svc-keycloak-http
位置OU=ServiceAccounts,DC=<domain>,DC=<tld>
密码策略永不过期
注意事项不要勾选"用户下次登录时须更改密码"
7.2.2 注册 SPN（Service Principal Name）

在域控上以域管理员身份运行：

setspn -S HTTP/<KEYCLOAK_DOMAIN> svc-keycloak-http

验证：

setspn -L svc-keycloak-http

应输出：HTTP/<KEYCLOAK_DOMAIN>

⚠️
SPN 中的域名必须与用户浏览器实际访问的域名完全一致。如果生产环境换域名，SPN 和 keytab 需要重做。
7.2.3 生成 keytab 文件

在域控上运行：

ktpass -out keycloak.keytab ^
  -princ HTTP/<KEYCLOAK_DOMAIN>@<DOMAIN>.CN ^
  -mapuser svc-keycloak-http@<DOMAIN>.CN ^
  -pass [REDACTED_PASSWORD] ^
  -crypto AES256-SHA1 ^
  -ptype KRB5_NT_PRINCIPAL
⛔
@<DOMAIN>.CN 必须全大写（Kerberos Realm 区分大小写）。生成 keytab 会重置该账号密码，确认 svc-keycloak-http 不被其他系统依赖。
✅
产出：keycloak.keytab 文件，安全传递给应用层团队。

7.3 Keycloak 侧配置（应用层团队操作）

7.3.1 上传 keytab 到 Keycloak 服务器

将 keycloak.keytab 放到 Keycloak 可访问的路径，如：

/opt/keycloak/conf/keycloak.keytab

确保 Keycloak 进程有读取权限。

7.3.2 在 LDAP User Federation 中启用 Kerberos

Keycloak 管理控制台 → 用户联盟 → 你的 LDAP Provider → 编辑：

Allow Kerberos authentication开
Use Kerberos for password authentication关（密码仍走 LDAP Bind）
Kerberos Realm<DOMAIN>.CN（全大写）
Server PrincipalHTTP/<KEYCLOAK_DOMAIN>@<DOMAIN>.CN
Key Tab/opt/keycloak/conf/keycloak.keytab

保存。

7.3.3 配置 Authentication Flow

Keycloak → 左侧 身份验证 → browser flow → 确认 Kerberos 步骤存在且启用：

browser flow:
  ├── Cookie (ALTERNATIVE)
  ├── Kerberos (ALTERNATIVE)        ← 确认启用
  └── forms (ALTERNATIVE)
        ├── Username Password Form
        └── ...

如果 Kerberos 步骤不存在，点击 Add step → 选择 Kerberos → 设为 ALTERNATIVE。

7.4 客户端浏览器配置（GPO 推送）

域内电脑需要将 Keycloak 域名加入浏览器的 Intranet 信任区，否则浏览器不会自动发送 Kerberos Ticket。

通过组策略（GPO）推送：

计算机配置 → 管理模板 → Windows 组件 → Internet Explorer → Internet 控制面板 → 安全页
  → 站点到区域分配列表 → 添加：
    值名称: <KEYCLOAK_DOMAIN>
    值: 1 (Intranet)

对于 Chrome/Edge，通过注册表或 GPO 设置：

[HKEY_LOCAL_MACHINE\SOFTWARE\Policies\Google\Chrome]
"AuthServerAllowlist"="*.<domain>.<tld>"
"AuthNegotiateDelegateAllowlist"="*.<domain>.<tld>"
