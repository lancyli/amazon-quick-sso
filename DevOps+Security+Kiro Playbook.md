# DevOps Agent + Security Agent + Kiro-CLI 通用 Playbook

---

## 1. Playbook 概述

### 1.1 定位
本 Playbook 提供一套 **"预防-发现-修复"全生命周期 DevSecOps 组合方案**，三个 AI Agent 各司其职、通过 MCP 集成形成闭环，可直接用于用户 Demo、Workshop 和方案设计。

### 1.2 核心价值
| 维度     | 价值                     | 参考数据                        |
| -------- | ------------------------ | ------------------------------- |
| 运维效率 | MTTR 大幅降低            | WGU: 2h → 28min (-77%)          |
| 主动预防 | 历史模式分析，提前发现隐患 | DevOps Agent 预防性建议        |
| 安全左移 | 设计阶段发现安全问题     | Security Agent 渗透测试         |
| 资源洞察 | 自然语言查询运维状态     | DevOps Agent SRE 自动化         |

## 2. 🎯 核心定位：三者的分工与选择

> **不是三选一，而是在问题生命周期的不同阶段各司其职**

```
 时间线 ──────────────────────────────────────────────────────▶

 ┌─── 事前预防 ───┐  ┌─── 事中发现+分析 ───┐  ┌─── 事中/事后修复 ───┐
 │                │  │                    │  │                    │
 │ Security Agent │  │  DevOps Agent      │  │    Kiro-CLI        │
 │                │  │                    │  │                    │
 │ • 渗透测试     │  │ • 事件集成主动响应  │  │ • 结合 AWS CLI 运维  │
 │ • 设计审计     │  │ • 按需分析（只读）  │  │ • IaC 开发/修复     │
 │ • 威胁建模     │  │ • 预防性建议        │  │ • 资源分析排查      │
 │ • 代码审查     │  │ • SRE 自动化巡检   │  │ • 人工确认执行      │
 │                │  │                    │  │                    │
 │ 扫描/测试权限  │  │ 只读权限           │  │ 用户IAM角色权限     │
 └────────────────┘  └────────────────────┘  └────────────────────┘
        │                      │                       │
        │            MCP 集成   │          MCP 集成     │
        └──────────────────────┴───────────────────────┘
```

### 2.1 各自定位精确描述

|              | Kiro-CLI                                                    | DevOps Agent                                    | Security Agent                          |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------ | ----------------------------------------- |
| **一句话**   | 开发者 AI 运维搭档：能查能改                                  | AI 值班员：主动发现，只看不改                     | 安全专家：主动找漏洞                       |
| **核心能力** | IaC 开发 + 资源分析 + 问题排查 + 修复执行                     | 主动事件响应 + 按需分析                           | 渗透测试 + 设计审计 + 威胁建模             |
| **运行环境** | **工作电脑 / 堡垒机**                                         | 云端（接入监控生态）                              | 云端                                       |
| **权限模型** | **继承用户 IAM 角色权限**（可读可写，受角色约束）              | **只读权限**（不做任何变更）                       | 扫描/测试权限（不改业务逻辑）              |
| **触发方式** | 人主动发起                                                    | **事件集成自动触发** / 人按需查询                 | PR 触发 / 按需发起                         |
| **与 AWS CLI** | **直接结合 AWS CLI 运维**（kubectl, aws cli, terraform）     | 通过 API 只读获取数据                             | 通过 API 发起安全测试                      |
| **关键差异** | 权限跟着人走，人确认后执行                                    | 与监控事件集成，7×24 无人值守                      | 专注安全维度                               |

```
│   └─ ▶ Security Agent（渗透测试 + 设计审计）

└─ "我们想全链路安全"

```

### 2.2 以 EKS+EFS 场景说明三者分工

> **问题：EKS Node 上 Pod 无法挂载 EFS**

| 阶段         | 谁              | 做什么                                                    | 权限                  |
| ------------ | --------------- | ---------------------------------------------------------- | --------------------- |
| **事前-预防** | Security Agent  | 渗透测试：扫描 EFS 端口暴露、SG 配置合理性                  | 安全扫描权限           |
| **事中-发现** | DevOps Agent    | 事件集成主动响应：CloudWatch 告警 → 自动调查 → 给出根因结论 | **只读**权限           |
| **事中-修复** | Kiro-CLI        | 在堡垒机用 AWS CLI 验证 → 生成 Terraform 修复代码 → 人工确认执行 | **用户 IAM 角色权限** |
| **事后-加固** | Security Agent  | 将此模式加入渗透测试用例                                    | 安全扫描权限           |
| **事后-学习** | DevOps Agent    | 学习修复模式 → 下次 SG 变更时主动预警                       | 只读权限               |

## 4. 🤝 结合使用：三个模式

### 模式 1：完整闭环（最佳实践 ⭐）
```
Security Agent 渗透测试 → 发现 SG 配置风险（事前）
                                              │
     问题真的发生了 ────────────────────────────┘
     │
     ▼ DevOps Agent 事件集成主动响应（只读权限）
     ├─ CloudWatch 告警自动触发
     ├─ 关联多信号分析
     └─ 推送根因结论（MCP + Slack）
           │
           ▼ Kiro-CLI（堡垒机，用户 IAM 角色权限）
           ├─ 通过 MCP 拉取 Agent 结论
           ├─ aws cli / kubectl 验证
           ├─ 生成 Terraform 修复代码
           └─ 人工确认执行 ✅
                │
                ▼ Security Agent 审查修复代码 + 更新渗透用例
                ▼ DevOps Agent 学习模式 → 下次主动预警
```

### 模式 2：Kiro-CLI 为主（快速排障场景）
```
开发者在堡垒机发现问题
     │
     ▼ Kiro-CLI + AWS CLI（用户 IAM 角色权限）
     ├─ kubectl describe pod / aws efs describe-mount-targets
     ├─ 分析日志 → 定位根因
     ├─ 生成修复命令 / IaC 代码
     └─ 人工确认执行 ✅
```
**适用**：快速排障、已知有问题、零配置启动

### 模式 3：DevOps Agent 为主 + Kiro 修复
```
DevOps Agent 7×24 事件集成主动响应（只读）
     │ 告警触发 → 自动调查
     ▼ 推送根因结论
                    │
                    ▼ Kiro-CLI 修复（用户 IAM 权限）
```
**适用**：生产环境持续监控、夜间无人值守

## 5. 💡 选型指南

### 5.1 常见问题解答

| 常见问题                                          | 回答                                                                                                                                          |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| "Kiro 和 DevOps Agent 都能分析日志，区别是什么？" | "**权限和触发方式不同**：Kiro 继承你的 IAM 角色权限，能查能改，但需要人主动发起；DevOps Agent 只有只读权限，但能与事件集成自动触发，7×24 主动响应。一个是'带工具的工程师'，一个是'只读监控大屏'。" |
| "为什么 DevOps Agent 不能执行修复？"              | "设计哲学是**只读**——生产环境变更必须经过人确认。Agent 负责发现和分析，Kiro 负责生成修复代码，人确认后执行。权限分离是最安全的模式。"           |
| "Security Agent 和另外两个什么关系？"             | "Security Agent 做**渗透测试**——主动找漏洞和暴露面，在问题发生之前就阻断。另外两个是问题发生后的发现和修复。三者是事前-事中-事后的关系。"       |
| "我们怕 AI 乱改生产环境"                          | "三层安全保障：DevOps Agent **只读不改**；Kiro-CLI **继承用户 IAM 权限**且需人工确认；Security Agent **审查修复代码**。"                        |

### 5.2 使用场景 → 快速推荐

| 场景描述              | 推荐                              | 原因                              |
| ---------------------- | ---------------------------------- | ----------------------------------- |
| "开发者在堡垒机排障"   | **Kiro-CLI**                       | 直接跑堡垒机 + AWS CLI，用户权限   |
| "凌晨出问题没人处理"   | **DevOps Agent**                   | 事件集成主动响应，只读权限         |
| "想做安全漏洞扫描"     | **Security Agent**                 | 渗透测试核心能力                   |
| "自动发现 + 手动修复"  | **DevOps Agent + Kiro-CLI (MCP)**  | 只读发现 + 用户权限修复            |
| "怕 AI 乱改环境"       | **三者结合**                       | 只读+用户权限+安全审查 = 三层保障  |
| "出海多区域合规"       | **Security Agent 为主**            | 渗透测试 + 合规映射                |

## 6. 典型场景 Playbook

### 场景 A：EKS Pod 无法挂载 EFS

```
Step 1: Pod 启动失败，挂载 EFS 超时
Step 2: Kiro-CLI（堡垒机）+ AWS CLI（用户 IAM 权限）→ 拉取日志
Step 3: 分析日志 → 定位根因（SG/子网/CSI driver）
Step 4: 生成修复代码（Terraform / AWS CLI 命令）
Step 5: 人工确认执行修复 ✅
```

### 场景 B：出海安全合规

```
Step 1: Security Agent → 渗透测试 + 合规审计
Step 2: Kiro-CLI → 生成合规修复代码
Step 3: DevOps Agent → 部署后持续只读监控
```

### 场景 C：7×24 EKS 主动运维

```
Step 1: DevOps Agent 事件集成（只读）→ 主动响应告警
Step 2: 自动调查 → 推送根因结论
Step 3: Kiro-CLI → 生成修复代码（用户 IAM 权限）
Step 4: Security Agent → 审查修复安全性
```
